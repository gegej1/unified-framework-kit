# Specify a bounded feature package

## Purpose

Turn a selected feature into a bounded `spec.md` that is ready for planning.

## Typical inputs

- project-local rules and constraints
- the currently selected feature from project memory
- clarified scope assumptions
- any existing user stories, acceptance criteria, or risk notes

## Typical outputs

- a feature-local `spec.md`
- explicit scope and non-scope
- acceptance criteria and evidence anchors
- assumptions that the plan must respect

## When to use

Use this when the team knows which feature is active and needs a durable feature definition before implementation planning starts.

## Recommended operator flow

1. Confirm the feature identity and its boundary with adjacent work.
2. Write user-visible outcomes and acceptance criteria first.
3. Capture assumptions instead of silently inventing project facts.
4. Keep the document feature-local rather than expanding into backlog or program management.

## Failure fallback

If you cannot define a stable `spec.md` yet:

- return to clarification
- split the feature into a smaller bounded unit
- stop before planning if acceptance still cannot be stated clearly

## Boundary reminder

- `specify` defines only the current feature package.
- It does not replace `longrun` as the owner of project facts or durable status.
- It does not define the execution method; it prepares inputs for the execution layer.
